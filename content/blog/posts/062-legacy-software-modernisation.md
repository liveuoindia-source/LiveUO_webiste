Many businesses run on software that has served them for a decade or more: a desktop application written by a developer who has since moved on, an old version of a package that's no longer supported, a database that only one person understands. It works — mostly — and replacing it feels risky.

The risk of not replacing it grows quietly: security gaps, no remote access, hardware that can't be replaced, and staff who spend their day working around it.

## Signs it's time

- the software runs only on old operating systems or hardware
- nobody can change it, or changes take weeks
- data can't be accessed outside the office
- you rely on exports and spreadsheets for basic reports
- security updates are no longer available
- one person holds all the knowledge

## Choose an approach

| Approach | What it means | When it fits |
|---|---|---|
| Replace with a product | Move to off-the-shelf software | Standard processes, good products exist |
| Rebuild | Write a new system | Process is unique, old system is unmaintainable |
| Modernise in place | Move the database, add web access, refactor | Core logic is sound |
| Step-by-step replacement | New modules take over one area at a time | Large systems, low tolerance for disruption |

For most mid-sized businesses, **step-by-step replacement** balances risk and progress best.

## Understand what the old system really does

Old systems hold years of rules that nobody wrote down: a discount that applies only to certain customers, a report adjusted for a quirk, a validation added after a mistake.

Capture them by:

- interviewing long-time users about exceptions and workarounds
- listing every report and who uses it
- reviewing the database for fields and tables that matter
- collecting real examples of unusual transactions

## Plan the data migration early

Data is usually the hardest part:

1. **Inventory** — what data exists, where, and in what condition.
2. **Clean** — duplicates, incomplete records, inconsistent codes.
3. **Map** — old fields to new ones, including derived values.
4. **Trial migrations** — repeat until totals, balances and counts match.
5. **Decide on history** — migrate everything, or only open items and recent history, with old data archived but searchable.

## Replace step by step

A typical sequence:

1. **Reporting first.** Build reports and dashboards on a copy of the old data. Quick value, no disruption.
2. **One module at a time** — for example, orders before accounting — with a sync between old and new.
3. **Pilot** each module with one team or branch.
4. **Switch over** once the module is proven, and retire that part of the old system.

## Keep the business running

- **Freeze changes to the old system** during migration, except urgent fixes.
- **Plan the cut-over** for a quiet period — not month-end or a festival season.
- **Have a rollback plan** for each step.
- **Train before go-live**, not after.
- **Support closely** for the first weeks.

## After modernisation

The new system should be easier to change, accessible securely from anywhere, backed up automatically, and documented — so you're never again dependent on one person's memory.

Modernisation doesn't need a big-bang project. Done in steps, with the data handled carefully and users involved throughout, it replaces old software without the business ever stopping.
